## 2. Flawed / Broken AI Code (Identified Hallucinations & Regressions)

Blind acceptance of AI-generated code was rejected. During development, several severe issues, security loopholes, and architectural breakages generated by AI models were actively detected and flagged:

### Instance 1: Next.js 16 Turbopack & CacheComponents Dynamic Collision
* **Issue Generated by AI:** AI scaffolding introduced `export const dynamic = "force-dynamic"` across server layout routes (`src/app/dashboard/layout.tsx` and verifier pages).
* **Failure Mode:** In Next.js 16 with `cacheComponents` active, `export const dynamic = "force-dynamic"` threw a hard build error:  
  `Route segment config "dynamic" is not compatible with nextConfig.cacheComponents. Please remove it.`
* **Consequence:** The entire dashboard crashed and refused to render in Turbopack dev and production builds.

### Instance 2: NextAuth v5 Middleware Recursive Deadlock & Infinite Spin
* **Issue Generated by AI:** Standard AI boilerplate configured Next.js `middleware.ts` with a global matcher `matcher: ["/((?!_next/static|_next/image|favicon.ico).*)"]`.
* **Failure Mode:** When NextAuth executed internal session callbacks at `/api/auth/session` and `/api/auth/callback/credentials`, the middleware intercepted the API request itself and invoked `auth()`, creating an unresolvable recursive loop.
* **Consequence:** The Login button spun infinitely with a hanging promise, and users were permanently locked out upon signing out or re-authenticating.

### Instance 3: Serverless Neon PostgreSQL Connection Pool Exhaustion on Cold Start
* **Issue Generated by AI:** The AI provided standard Prisma initialization (`new PrismaClient()`) with a default connection string without serverless pooling parameters.
* **Failure Mode:** Under Neon's serverless autosuspending compute, the database goes cold after idle periods. Default timeouts (5 seconds) timed out with `PrismaClientInitializationError: Can't reach database server`.
* **Consequence:** Verification transitions failed intermittently in production with HTTP 500 errors.

### Instance 4: Client-Side Bypassable Hard Stop & Missing Wastage Audit Log
* **Issue Generated by AI:** Initial AI suggestions attempted to disable the "Approve Batch" button strictly using client-side React state (`disabled={hasRed}`), but failed to enforce server-side validation or compute fabric wastage variance.
* **Failure Mode:** Anyone sending a direct cURL or Postman `POST` request to `/api/verification/:orderId` with `{ decision: "APPROVED" }` could bypass frontend validation and approve shortage batches. Furthermore, `wastagePct` in `verification_logs` was left `null`.

## 3. Human Refactoring & Engineering Hardening

To transform raw code into resilient, production-ready enterprise software, the following human refactoring was implemented:

1. **Resolution of Next.js 16 Cache Protocol:**
   - Removed conflicting `dynamic = "force-dynamic"` segments.
   - Configured `export const instant = false` as mandated by Next.js 16 when reading dynamic headers and authentication sessions in layout components.
2. **Middleware Deadlock Decoupling:**
   - Hardened `middleware.ts` matcher pattern to `matcher: ["/((?!api|_next/static|_next/image|favicon.ico).*)"]`.
   - Ensured all `/api/*` endpoints handle their own granular server-side RBAC checks without middleware deadlock.
   - Replaced fragile router pushes with `window.location.href = "/dashboard"` on login to ensure clean browser state and token synchronization.
3. **Resilient Neon PostgreSQL Connection Pooling:**
   - Appended `&connect_timeout=30&pool_timeout=30` to connection strings to smoothly survive cold starts.
   - Initialized a global singleton Prisma client with connection retry resilience.
4. **Server-Side Hard Stop Implementation (422 Unprocessable Entity):**
   - Implemented a non-bypassable backend loop iterating every `verificationItem`. If `actualQty < expectedQty`, the server instantly aborts with HTTP `422`, rolling back any state change.
   - Added automated calculation of Fabric Wastage Percentage:
     $$\text{Fabric Wastage \%} = \frac{\text{Actual Fabric Used} - \text{Expected Fabric}}{\text{Expected Fabric}} \times 100$$
   - Stored the computed wastage percentage inside the immutable `verification_logs` table.
5. **UI Accessibility & Zero-Contrast Remediation:**
   - Replaced low-contrast inputs with high-contrast `bg-slate-900 border-slate-700 text-white placeholder-slate-400`.
   - Explicitly styled HTML `<select>` option elements with dark backgrounds and white text to prevent white-on-white text clipping in Chromium browsers on Windows.

## 4. Defensive Architecture & Security State Machine

The system enforces defensive architecture at multiple tiers to guarantee that business logic cannot be tampered with:

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                       MANUFACTURING STATE MACHINE                           │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│  [1. CUTTING_IN_PROGRESS] ──(Supervisor submits)──► [2. PENDING_VERIFICATION]
│                                                            │                │
│                                                     (Verifier QC)           │
│                                                       ┌────┴────┐           │
│                                              (Shortage)       (Valid)       │
│                                                  ▼                 ▼        │
│                                            [REJECTED]       [3. VERIFIED]   │
│                                        (Mandatory Note)            │        │
│                                                               (Auto Handoff)│
│                                                                    ▼        │
│                                                           [4. SEWING_QUEUE] │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘
```

### Architectural Safeguards

1. **Deterministic State Invariants:**
   - Orders can only move from `CUTTING_IN_PROGRESS` to `PENDING_VERIFICATION` by a verified `cutting_supervisor`.
   - Orders can only be approved/rejected when in `PENDING_VERIFICATION` by a verified `cutting_verifier`.
   - State cannot skip forward directly to `SEWING_IN_PROGRESS`.
2. **Server-Side RBAC (HTTP 403 Forbidden):**
   - User identity and role are strictly decoded from the verified server-side JWT session (`auth()`).
   - A `cutting_supervisor` sending a POST to `/api/verification/:orderId` receives an immediate 403 Forbidden.
   - A `cutting_verifier` cannot create orders or initiate sewing assembly.
3. **Database-Level Query Isolation:**
   - The Sewing Queue endpoint (`/api/sewing/queue`) and dashboard page strictly execute:
     `prisma.cuttingOrder.findMany({ where: { status: { in: ['VERIFIED', 'SEWING_IN_PROGRESS'] } } })`.
   - URL parameter tampering cannot expose unverified, pending, or rejected batches to sewing machine operators.
4. **Immutable Audit Trail:**
   - Every verification decision is permanently recorded in `verification_logs` with verifier ID, decision (`APPROVED` | `REJECTED`), mandatory rejection notes, computed fabric wastage percentage, and UTC timestamp.
   - Audit logs have no update or delete endpoints.
5. **Defensive Input Validation:**
   - Quantities are strictly guarded against non-numeric payloads, floating points in integer fields, and negative numbers.
   - Rejection requires a non-empty string note (`rejectionNote.trim().length > 0`), rejected with 422 if empty.
